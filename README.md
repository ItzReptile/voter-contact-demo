# voter-contact-demo

**Doorstep** is a small voter contact tool I built to show how I'd work on a tool like [Matchbook](https://indigo.engineering): import a voter file, cut phone lists and door-knocking turfs, assign them to volunteers, log every contact attempt, and see contact rates and support IDs by day, precinct and list.

It is a demo, not campaign software I've shipped. **Every voter in it is generated by a script.** Names and addresses come from [Faker](https://fakerjs.dev), and phone numbers use area code 555, which isn't in service.

TypeScript, Next.js 16, React 19, Postgres, Tailwind. Built with Claude Code; [how that worked](#how-i-built-it-with-claude-code) is below.

**Live demo: [voter-contact-demo.vercel.app](https://voter-contact-demo.vercel.app)**. No sign in. The data resets every night, so click around freely.

## What it does

One loop of a field program:

1. **Import a voter file** (`/voters/import`). Upload a CSV. Each row is validated on its own: bad rows are skipped and listed by line number ("Line 6: age must be at least 18"), good rows import. Re-uploading the file updates voters by `voter_id` instead of duplicating them.
2. **Browse voters** (`/voters`). Search by name, address or voter ID, filter by precinct and party, sort any column, page through. Everything lives in the URL.
3. **Build a segment** (`/lists/new`). Filter by precinct, party, age range, support score range, and contact history (never attempted / not yet reached). The match count and a preview update as you change filters.
4. **Cut a list.** A list is a snapshot of who matched, numbered in **walk order** for doors (precinct, street, house number) or alphabetically for calls. Phone lists leave out voters with no number.
5. **Assign it to a volunteer** (`/lists`, or on the list). Contacts can't be logged on an unassigned list, so every attempt is credited to someone.
6. **Canvass** (`/lists/[id]/canvass`, or from a volunteer's "my lists" page). Volunteer mode: a phone first page without the organizer's header, with one way back. One voter at a time in list order: one tap logs a conversation with a 1 to 5 support ID (1 = strong support), not home, or moved/wrong number, with an optional note, and moves to the next door. A mis-tap can be undone for 2 minutes. Every attempt is kept, so a not-home can be knocked again.
7. **Report** (`/dashboard`). Contact rate (conversations ÷ attempts), attempts per day by outcome, support IDs, contact rate by precinct, and progress by list.

The home page (`/`) explains the demo and links into it.

`npm run seed` loads 2,397 voters across 12 precincts, 5 volunteers, 6 lists and a few hundred attempts, so every page has something on it. The sample file ([public/sample-voters.csv](public/sample-voters.csv), also downloadable from the Voters page) has 3 rows that are bad on purpose, to show the import report.

## Run it

You need Node 24+ and Docker (or any Postgres 14+; put its URL in `.env`).

```bash
git clone https://github.com/ItzReptile/voter-contact-demo.git
cd voter-contact-demo
npm install
cp .env.example .env
docker compose up -d     # Postgres on port 5433, with a dev and a test database
npm run seed             # wipes the dev database and loads demo data
npm run dev              # http://localhost:3000
```

## Tests

| Command | What runs |
|---|---|
| `npm run test:unit` | CSV parsing and validation, address splitting, segment → SQL, rate math. No database. |
| `npm test` | The unit tests plus database tests against a real Postgres: import upserts, list snapshots and walk order, contact rules, dashboard numbers on a known fixture. |
| `npm run test:e2e` | Playwright on a production build: upload a CSV with a bad row → build a segment and watch the count → create a turf → assign it → canvass it (a conversation, a not-home, a skip) → check the dashboard. Plus the voter table's search, filters and sorting, and every main page at 390px wide. |
| `npm run check` | Lint, typecheck, unit and database tests. |

[GitHub Actions](.github/workflows/ci.yml) runs all of it on every push, with Postgres as a service container.

## How it's built

```
Browser
  │  GET a page
  ▼
Page (Server Component)  ──►  src/lib/*.ts  ──►  Postgres
  │  renders HTML on the server; no API layer in between
  │
  │  submit a form
  ▼
Server Action (actions.ts)  ──►  zod validation  ──►  src/lib/*.ts  ──►  Postgres
                                                        then refresh() re-renders the page
```

- **`src/lib/`** holds all the domain logic and every SQL query, one file per area (voters, lists, contacts, volunteers, dashboard). Pages and actions stay thin.
- **Plain SQL with the `pg` driver.** The queries are the interesting part of this app (turning a segment into a `WHERE` clause, snapshotting a list in walk order with `row_number()`, a bulk upsert with `unnest()`), so they're visible rather than generated by an ORM. Every value is a `$n` parameter.
- **The database enforces the rules too.** Check constraints for every enum, a constraint that a support ID needs a conversation, and a composite foreign key so a contact can only be logged for a voter who is on that list. The UI and the zod schemas prevent these first; the database is the backstop.
- **The segment builder is a GET form.** The server reads the filters from the URL, renders the count and preview, and "Create list" posts the same filters (validated again) to a Server Action. No client-side state to keep in sync.
- **Each page renders its frame immediately** and streams its data inside `<Suspense>`, with a skeleton shaped like the page, which is how Next.js 16 with Cache Components expects data pages to be written. The build never touches the database.
- **One visual direction: the door hanger.** It looks like the card a volunteer leaves on the knob: two spot inks on bright card stock. Indigo is the product and its actions; orange is the outcome that matters, a conversation. Archivo condensed carries the headings and big numbers. Three directions were prototyped side by side on the real data before this one was chosen. The mechanics (named text styles defined once in `globals.css`, a fixed spacing scale, skeletons, empty and error states, 390px checks) follow [.claude/skills/landing-page-design](.claude/skills/landing-page-design/SKILL.md). Charts are plain HTML and SVG with hover and keyboard tooltips and a hidden table for screen readers.

The full plan, with the reasoning for each decision, is in [docs/plan.md](docs/plan.md).

## How I built it with Claude Code

Claude Code did most of the typing. What makes an agent useful on a codebase is the context, the guardrails and the review around it, and those are in the repo:

- **A plan before code.** [docs/plan.md](docs/plan.md) was written first: data model, definitions (what counts as a conversation, what contact rate means), test plan, milestones. It changes in the same commit as any decision it records.
- **A context file for the agent.** [CLAUDE.md](CLAUDE.md) has the commands, a map of the code, the domain terms, and the rules: parameterized SQL only, validate at the boundary, fake data only, how pages are shaped in this version of Next.js, and what "done" means. It was written before the UI, so the UI followed it.
- **Skills.** [landing-page-design](.claude/skills/landing-page-design/SKILL.md) is my design system: every UI change follows it, so the agent doesn't invent font sizes, spacing or colors. [add-segment-filter](.claude/skills/add-segment-filter/SKILL.md) walks through the most common change: the five places a new filter touches, in order, test first.
- **Tests at the cheapest level that can catch each bug.** Pure functions get unit tests; anything with SQL runs against a real Postgres; one end-to-end test covers the whole loop. The test helpers refuse to wipe any database whose name doesn't end in `_test`.
- **CI as the gate.** Nothing is done until lint, typecheck, the database tests and the Playwright run pass.

Running the app, not just the unit tests, caught bugs that each now have a test or a rule in CLAUDE.md:

- After assigning a list, the volunteer dropdown snapped back to "Unassigned" even though the database had saved it. React 19 resets a form after its action runs, and a reset `<select>` returns to the `defaultValue` it was first rendered with. Fix: key the select by the saved value so it remounts. The end-to-end test checks the dropdown after assigning.
- The voter table pushed the whole page sideways. A CSS grid track grows to fit a wide table's minimum width, so the table's own scroll container never kicked in. Fix: a flex column (or `minmax(0, 1fr)` tracks) around wide tables. The end-to-end test now checks every main page at 390px wide.
- On the dashboard, hover tooltips on the rightmost chart columns were centered on their column and stuck out past the page edge, which made the page scroll sideways on narrow screens even while hidden. They now open toward the middle of the chart.
- The list builder rendered "4voters match": two styled spans with no space between them, which is also what a screen reader would announce. The end-to-end test caught it by reading the text.
- The dev server flagged every data page as blocking navigation in Next.js 16. Each page now renders its frame and wraps its data in `<Suspense>` with a skeleton; CLAUDE.md describes the pattern so new pages follow it.

## Deploy

The live demo runs on [Vercel](https://vercel.com) with a [Neon](https://neon.tech) Postgres database. The build needs no database; only the running app does.

1. Push the repo to GitHub and import it as a Vercel project (`vercel link`, then `vercel git connect` so every push deploys).
2. Add a Neon database to the project from the Vercel Marketplace (Storage → Neon). It sets `DATABASE_URL` for you.
3. Add a secret for the nightly reset: `vercel env add CRON_SECRET production` with a long random value.
4. Deploy: `vercel deploy --prod`.
5. Load the demo data into the hosted database:

   ```bash
   vercel env pull .env.production.local --environment=production
   npm run seed:production
   ```

   `.env.production.local` is gitignored. `npm run seed` on its own refuses any database that isn't on localhost.

Because there is no sign in, anyone can change the hosted data. [vercel.json](vercel.json) schedules a cron job that calls `/api/reset-demo` every night at 08:00 UTC, which reloads the generated data. The route rejects any request without `CRON_SECRET`.

## What's missing

This is a demo of the workflow, not a product. A real version needs:

- **Auth and per-campaign isolation.** Right now anyone with the URL can do anything. Volunteers should see only their own lists, and every table needs a campaign boundary (row-level security or a `campaign_id`).
- **Turf cutting.** Splitting one universe into turfs of N doors, ideally by geography.
- **Smarter re-contact rules**, like keeping wrong numbers off future phone lists.
- **Background imports.** A real voter file is millions of rows; this one imports a few thousand in one request.
- **An audit log** of who changed what.
