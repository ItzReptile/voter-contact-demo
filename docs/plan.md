# Technical plan

Written before the code. It records what the app does, the decisions behind it, and how each part is tested. When a decision changes, this file changes in the same commit.

## Goal

A small voter-contact tool that covers one full loop of a field program:

1. **Import** a voter file (CSV).
2. **Segment** it into a universe: precinct, age range, support score range, party, contact history.
3. **Cut a list** from that universe: a phone list or a door-knocking turf, in call or walk order.
4. **Assign** the list to a volunteer.
5. **Log contacts**: reached / not home / wrong number, a 1-5 support ID, notes.
6. **Report**: attempts, conversations, contact rate, and support IDs by precinct and by list.

All data is generated by `scripts/generate-voters.ts`. No real voter data, ever.

## Non-goals

- Authentication and permissions. Anyone with the URL can do anything. A real tool needs logins, per-campaign data isolation, and volunteers who see only their own lists.
- A mobile canvassing app, maps, or automatic turf cutting by geography.
- Modeling. The support score arrives in the voter file, the way a campaign would receive one from a modeling vendor.

## Stack

| Part | Choice | Why |
|---|---|---|
| UI and server | Next.js 16 (App Router), React 19, TypeScript | One deployable app. Server Components read the database directly; Server Actions handle writes. |
| Styling | Tailwind CSS 4 | No custom CSS to maintain. |
| Database | Postgres 17, `pg` driver, plain SQL | The queries are the interesting part of this app, so they stay visible instead of hidden behind an ORM. Every query is parameterized. |
| Validation | zod | One schema per input (CSV row, segment, contact) shared by the UI and the server. |
| CSV parsing | papaparse | Handles quoting, BOMs and line endings. |
| Tests | Vitest (unit + database), Playwright (end to end) | |
| CI | GitHub Actions with a Postgres service container | Lint, typecheck, unit + database tests, build, end-to-end test. |

## Data model

```
volunteers (id, name)

voters     (id, voter_file_id UNIQUE, first_name, last_name,
            address, house_number, street, city, zip,
            precinct, age, party, phone, support_score 0-100)

lists      (id, name, kind 'phone'|'door', segment jsonb, volunteer_id → volunteers)

list_voters(list_id → lists, voter_id → voters, position)      PK (list_id, voter_id)

contacts   (id, list_id, voter_id, volunteer_id, outcome, support 1-5, notes, created_at)
            FK (list_id, voter_id) → list_voters
```

Decisions:

- **`voter_file_id` is the import key.** Uploading the same file twice updates rows instead of duplicating them (`INSERT ... ON CONFLICT DO UPDATE`).
- **A list is a snapshot.** Creating a list copies the matching voter IDs into `list_voters` with their order. Re-importing the file or logging contacts never changes who is on a list a volunteer is already working. The segment that produced it is kept in `lists.segment` for reference.
- **A contact must belong to a voter on that list.** The composite foreign key `(list_id, voter_id) → list_voters` makes the database reject anything else.
- **Every attempt is a row.** Knocking a door twice gives two rows. "Latest outcome" is computed, not stored.
- **Support ID only with a conversation.** A check constraint allows `support` only when `outcome = 'reached'`.
- **Address is split on import** into `house_number` and `street` so door lists can be sorted in walk order (precinct, street, house number).

## Definitions

| Term | Meaning here |
|---|---|
| Support score | 0-100 from the voter file: modeled likelihood of supporting our side. |
| Support ID | 1-5 recorded in a conversation. 1 = strong support, 3 = undecided, 5 = strong oppose. |
| Attempt | Any logged contact, whatever the outcome. |
| Conversation | An attempt with outcome `reached`. |
| Contact rate | Conversations / attempts. |
| Not yet reached | No `reached` attempt on any list. Not-homes stay eligible for another try. |
| Never attempted | No attempt of any kind. |

## Segment filters

A segment is one zod-validated object:

```ts
{ precincts: string[], parties: string[], minAge?, maxAge?, minScore?, maxScore?,
  contact: 'any' | 'never_attempted' | 'not_reached' }
```

`buildSegmentWhere(segment, kind)` turns it into a SQL `WHERE` clause plus a parameter array. It is a pure function, so most of the filter logic is unit tested without a database. Phone lists also require `phone IS NOT NULL`.

The segment builder is a plain GET form: the filters live in the URL, the server renders the match count and a sample of voters, and "Create list" posts the same filters to a Server Action. No client-side state to keep in sync, and a segment can be shared as a link.

## Next.js 16 notes

- `cacheComponents` is on, so data is dynamic by default. Every page has the same shape: the page component renders what doesn't need data (title, forms) and wraps one async component in `<Suspense>`. That component calls `await connection()` before its first query. Result: navigation shows the page frame instantly, Next never runs a query at build time, and the build needs no database.
- Mutations are Server Actions that call `refresh()` so the current page re-renders with new data.
- React 19 resets a form after its action runs. Selects whose value comes from the server are keyed by that value so they remount with it; placeholder options are not `disabled`, because a reset select falls back to its first enabled option.
- Routes stay mounted but hidden after navigation (React `<Activity>`). End-to-end tests use `getByRole`/`getByLabel`, which skip hidden elements.

## Test plan

| Layer | What | Where |
|---|---|---|
| Unit | CSV parsing and row validation, address splitting, segment → SQL, rate math | `src/lib/*.test.ts` |
| Database | Import upsert counts, list snapshot and order, contact constraints, dashboard numbers on a known fixture | `src/lib/*.db.test.ts`, against `TEST_DATABASE_URL` |
| End to end | Upload a CSV with one bad row → build a segment → create a turf → assign → log two contacts → dashboard shows them | `e2e/` |

The database helpers refuse to reset any database whose name does not end in `_test`.

## Later (not in this demo)

- Auth and per-campaign isolation (row-level security or a `campaign_id` on every table).
- Cutting one universe into several turfs of N doors each.
- Excluding wrong numbers from future phone lists.
- Audit log of who changed what.
- Background import for large files (a real voter file is millions of rows; this one is a few thousand and imports in one request).
